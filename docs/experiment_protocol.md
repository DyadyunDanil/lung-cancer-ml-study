# Общий протокол ML-экспериментов

## Назначение

Обеспечить сопоставимые и воспроизводимые условия для сравнения PLCOm2012,
логистической регрессии, Random Forest, XGBoost и MLP на синтетических данных.

Документ фиксирует общие методологические правила. Конкретные параметры сценариев
(объём выборки, механизм генерации, схема валидации и др.) указываются в
соответствующих ноутбуках. Ниже отдельно описаны настройки первого контрольного
сравнения, которые не обязательно применяются без изменений ко всем экспериментам.

## 1. Данные и сценарии

- Первый контрольный сценарий: `generate_baseline(n, seed)`.
- Целевая переменная: `y` — бинарная метка, сгенерированная из распределения Bernoulli с вероятностью `risk`.
- Признаки: только 11 столбцов из `FEATURE_COLUMNS` в `src/preprocessing.py`.
- Запрещённые признаки: `logit_base`, `logit_true`, `risk`, `y` и любые другие промежуточные сведения генератора.
- В контрольном сценарии *сама PLCOm2012 задаёт истинный риск*; это проверка на синтетических данных, а не доказательство превосходства PLCOm2012 на реальных пациентах.
- В последующих сценариях механизм генерации признаков и/или исходов может изменяться; такие изменения явно описываются в соответствующем ноутбуке.

## 2. Разбиение

Для первого контрольного сравнения:

- Стратифицированное `train/validation/test` = 60% / 20% / 20%.
- Фиксируем отдельные случайные числа для генерации (`seed`) и разбиения (`split seed`).
- Train: обучение моделей и подгонка преобразований.
- Validation: выбор порога по специфичности.
- Test: финальная оценка без изменения порога или параметров.

Важно: при `n=10_000` и распространённости около 0,86% в test ожидается
всего около 17 положительных меток. Поэтому для первых сравнений разумно
увеличить `n` (например, до 50_000), а далее провести анализ устойчивости
по нескольким независимым генерациям.

В экспериментах с подбором гиперпараметров, обучающими кривыми и повторными
генерациями схема разбиения может меняться, но тестовые данные не должны
использоваться для выбора модели, гиперпараметров или порога.

## 3. Предобработка

- Масштабирование числовых признаков с `StandardScaler`, обучаемым *только* на обучающих данных соответствующего разбиения.
- Бинарные признаки передаются без изменений.
- `race` кодируется `OneHotEncoder(handle_unknown="ignore")`.
- На первом этапе `education` рассматривается как порядковый числовой признак.
- Преобразователь для ML-моделей помещается в `sklearn.pipeline.Pipeline`.
- PLCOm2012 получает исходные значения признаков; масштабировать их до применения формулы нельзя.

## 4. Порог и метрики

Основная целевая метрика: Recall при пороге, выбранном на validation так,
чтобы **Specificity(validation) ≥ 90%**.

- Выбор: самый низкий порог, удовлетворяющий ограничению валидации, при правиле `p >= threshold`.
- На test используется **тот же порог**, без подгонки.
- Отчёт: Recall, фактическая test Specificity, TP/FP/FN/TN, ROC AUC, Average Precision (AP), Brier score.
- Дополнительно: стандартизованная частичная ROC AUC для FPR ≤ 0,10 (это не обычная площадь в диапазоне 0–0,1).
- Test Specificity может оказаться ниже 90% из-за выборочной вариабельности; это нужно честно сообщить.

## 5. Сравнение моделей и ограничения

- В пределах одного сравнительного эксперимента алгоритмы используют одинаковые обучающие и тестовые данные (либо одинаковые фолды при кросс-валидации).
- Настройка гиперпараметров выделяется в отдельный эксперимент с корректной внутренней валидацией (например, nested CV); нельзя выбирать параметры по итоговому test.
- Из-за редкого положительного класса обязательно указывать число положительных наблюдений и неопределённость результатов.
- Синтетические результаты не являются клинической валидацией, а FP модели риска не равны ложноположительным результатам КТ.
